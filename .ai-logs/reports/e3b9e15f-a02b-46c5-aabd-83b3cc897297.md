# Session Report: AI Analysis Async Job Client Integration

## Summary

Executed the previously-written implementation plan
(`docs/superpowers/plans/2026-08-06-ai-analysis-async-job-integration.md`)
via the subagent-driven-development workflow: replaced the app's synchronous
`POST /v1/ai/analyze` call with the new async create-and-poll job API
(`POST /v1/ai/analyses` + `GET /v1/ai/analyses/:id`), and replaced
`AnalyzingScreen`'s fake, timer-driven progress simulation with real
stage-by-stage progress driven by the backend's poll responses.

Work happened in an isolated git worktree (branch
`worktree-ai-analysis-async-job-integration`) to protect `main`. Five tasks
were each implemented by a fresh subagent and reviewed by a separate
reviewer subagent (one task required one fix-and-re-review round for an
inaccurate self-review claim, not a code defect). After all five tasks
passed review, a final whole-branch review by a more capable model
surfaced three additional cross-task issues; the user was consulted on the
two that involved deviating from the plan's literal text, approved fixing
all three, and a fix wave was applied and re-verified. The branch was then
fast-forward merged into `main` locally (user's explicit choice), the
worktree removed, and the feature branch deleted.

Final state on `main`: 6 test suites / 70 tests passing
(`yarn test src/modules/ai-analysis src/shared/api --runInBand`), lint
clean, `tsc` clean for all touched files. A full-repo `yarn test` run showed
168/169 passing, with the sole failure being a pre-existing, unrelated test
(`materialIconsSubset.test.ts`) whose relative-path arithmetic assumes a
fixed directory depth and breaks when run from inside a nested worktree —
confirmed independent of this change and not touched.

## Changed files

All paths below are relative to the repo root; they were edited inside the
worktree during the session and now exist at these same paths on `main`
after the merge (the worktree itself, and the `.superpowers/sdd/*.md`
subagent report/brief files the hook listed under the worktree path, were
build/coordination artifacts local to the worktree and no longer exist —
the worktree was removed as part of finishing the branch).

- **`src/shared/api/types.ts`** — Added `AnalysisJobStage`,
  `AnalysisJobProgressBody`, `CreateAnalysisJobSuccessBody`,
  `AnalysisJobStatusBody`, and 9 new `ApiErrorCode` literals
  (`VALIDATION_MISSING_IDEMPOTENCY_KEY`, `IDEMPOTENCY_CONFLICT`,
  `AI_STAGE_PROVIDER_ERROR`, `AI_STAGE_INVALID_OUTPUT`, `AI_STAGE_TIMEOUT`,
  `AI_JOB_TIMEOUT`, `AI_FINAL_VALIDATION_FAILED`, `AI_JOB_NOT_FOUND`,
  `AI_POLL_GIVE_UP`) needed to describe the async job API's request/response
  shapes. Purely additive — no existing type removed or narrowed.
- **`src/modules/ai-analysis/types.ts`** — Added `AnalysisProgress`,
  `AnalysisProgressCallback`, and a cancellation branch
  (`{ok: false; cancelled: true}`) on `AnalyzeTextResult`, so the UI seam
  can express "the user navigated away mid-analysis" distinctly from a real
  API failure.
- **`src/shared/api/analysisJobClient.ts`** (new) — The create-and-poll
  client. Exports `runAnalysisJob()`: posts a job with a fresh
  Idempotency-Key, resolves the returned `status_url`, polls on a
  Retry-After-then-fixed-1.5s cadence up to a 75s deadline, classifies
  poll responses as transient (retry) vs. terminal (return), validates
  completed job data via the existing `validateAIOutput`, and reports
  progress through an immutable-snapshot callback. Replaces
  `src/shared/api/analyzeClient.ts` (deleted, see below).
- **`src/shared/api/__tests__/analysisJobClient.test.ts`** (new) — 34 tests
  covering create success/error, all poll-response branches (transient,
  terminal, malformed), `Retry-After` parsing/capping, the 75s give-up
  timeout, abort at four distinct points, and progress-snapshot
  immutability, using fake timers and mocked `fetch`.
- **`src/shared/api/analyzeClient.ts`** (deleted) — Dead code once the async
  client fully replaced the synchronous endpoint in-app.
- **`src/shared/api/__tests__/analyzeClient.test.ts`** (deleted) — Coverage
  moved to `analysisJobClient.test.ts`.
- **`src/modules/ai-analysis/MockAIAnalysisService.ts`** — Replaced the
  immediate mock resolution with `simulateAnalysisJob()`, which emits
  synthetic progress through the same six backend stages (weighted
  15/35/25/10/10/5) on a short timer before resolving with the existing
  fixture data, so dev/demo mode exercises the same progress-rendering
  code path as production.
- **`src/modules/ai-analysis/__tests__/MockAIAnalysisService.test.ts`** —
  Updated to assert staged progress ordering, snapshot immutability, and
  cancellation for `simulateAnalysisJob`.
- **`src/modules/ai-analysis/AIAnalysisService.ts`** — `analyzeText()` now
  accepts an optional progress callback and `AbortSignal`, threads both to
  whichever runner `useMockAi` selects (`runAnalysisJob` or
  `simulateAnalysisJob`), and short-circuits before completion analytics on
  a cancelled result so `ai_analysis_completed` never fires for a
  cancelled run.
- **`src/modules/ai-analysis/__tests__/AIAnalysisService.test.ts`** —
  Updated to mock `analysisJobClient`/`MockAIAnalysisService` instead of
  the old synchronous client, and to assert callback/signal forwarding and
  cancellation analytics behavior.
- **`src/modules/ai-analysis/AnalyzingScreen.tsx`** — Removed the fake
  `setInterval`-driven 3-step progress simulation entirely. Now renders six
  static stage labels whose per-row status is derived from real
  `progress.stages[]` data, shows the backend's real percent/message, and
  creates an `AbortController` whose signal is passed to `analyzeText` and
  aborted on unmount so polling can't continue after the user navigates
  away.
- **`src/modules/ai-analysis/__tests__/AnalyzingScreen.test.tsx`** —
  Rewritten to drive progress via the captured callback directly (rather
  than relying on internal timers) and to assert rendering for every stage
  status combination, success/failure/cancellation paths, and
  abort-on-unmount.
- **`src/store/useScanStore.ts`** — One-line fix (found by the final
  whole-branch review, not part of the original plan): narrowed the
  widened `AnalyzeTextResult` union (`if (result.cancelled) return;`)
  before reading `.message`, restoring a clean `tsc --noEmit` on this
  untouched call site that Task 1's type change had silently broken.
- **`docs/superpowers/plans/2026-08-06-ai-analysis-async-job-integration.md`**
  — The implementation plan this session executed (already existed as an
  untracked file at session start; now committed as part of Task 1's
  commit).

Two additional fixes went beyond the original plan's literal text, made
only after asking the user and getting explicit approval, since they
address genuine gaps rather than deviations from an already-approved
design:
- **`src/shared/api/analysisJobClient.ts`** — Added `MAX_RETRY_AFTER_MS`
  (10s) cap so a server-sent `Retry-After` of e.g. 200s can no longer burn
  the entire 75s deadline in a single wait with zero polls issued. Added a
  per-request timeout (`FETCH_TIMEOUT_MS`, 10s, bounded by the remaining
  deadline) via a small manual `withTimeout()` helper — deliberately not
  using `AbortSignal.any`/`AbortSignal.timeout` due to React
  Native/Hermes runtime-support uncertainty — so a single hung `fetch`
  can no longer run past the stated 75s budget.
- **`src/modules/ai-analysis/AnalyzingScreen.tsx`** — Clamped the percent
  label to the same `[0,100]` range as the progress bar, so an
  out-of-range `percent` value can no longer show e.g. `-10%` or `150%`
  next to a bar pinned at `0%`/`100%`.

## User review

- **Merged directly to `main` locally**, per your explicit choice in this
  session, without pushing or opening a PR. If you expected a PR for
  visibility/CI, let me know and I can still push the (already-merged)
  history or open one from `main`.
- **Sync-path removal is irreversible in-app**: `src/shared/api/analyzeClient.ts`
  and its test are deleted; there is no feature flag to fall back to the
  old synchronous `/v1/ai/analyze` endpoint. If the backend's async job API
  isn't fully deployed everywhere this app is used, this is a hard
  dependency now.
- **Two deliberate deviations from the written plan** (both approved by you
  mid-session): capping `Retry-After` at 10s (the plan said to honor it
  as-sent, clamped only by the overall deadline) and adding a per-request
  fetch timeout (the plan only checked the deadline between attempts). Both
  are safety improvements, but worth knowing the shipped behavior differs
  from the plan document's literal text in these two respects.
- **Known residual gap, not fixed**: the new per-request timeout wraps
  `fetch()` but not the subsequent `response.json()` body read — a stalled
  response body can still run unbounded, and a user cancellation arriving
  mid-body-read no longer aborts the underlying stream (the abort listener
  is cleaned up before the read starts). Flagged by the final reviewer as
  a residual, non-blocking gap.
- **Tracked-but-not-fixed follow-up backlog** (all Minor severity per
  review, none blocking): no test for Idempotency-Key freshness across
  calls; no test asserting `signal`/`Accept` header/POST body actually
  reach `fetch`; `VALIDATION_TEXT_TOO_LONG` → `TEXT_TOO_LONG_MESSAGE`
  mapping untested; `MockAIAnalysisService.ts` duplicates small
  abort/cancellation helpers already in `analysisJobClient.ts`; one
  same-tick abort-race guard lacks an explanatory comment; no test drives
  a real external abort through a `fetch` that itself respects the signal.
- **Environment note, not a code issue**: a full-repo `yarn test` run shows
  one pre-existing failure in `src/components/icons/__tests__/materialIconsSubset.test.ts`,
  unrelated to this feature — its hardcoded relative-path traversal to
  `node_modules` assumes a fixed checkout depth and breaks specifically
  when tests run from inside a nested git worktree. Confirmed via direct
  file inspection that it's a pre-existing path-depth fragility, not a
  regression; no source file for this test was touched.
- **Repo has no `tsc`-based typecheck script or CI gate**: the
  `useScanStore.ts` type error above shipped invisibly through 3 of the 5
  per-task reviews because neither `yarn test` (Babel-transpiled, types
  stripped) nor `yarn eslint` type-checks. The final whole-branch review
  caught it by running `tsc --noEmit` directly. Worth considering a
  `typecheck` script and/or CI step so this class of issue is caught
  automatically in the future — flagged as a recommendation, not acted on
  in this session.
