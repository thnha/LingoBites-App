## User review

### Critical findings requiring action:

1. **Blocking gap identified**: The four SRS tables required for Stage 2 implementation do not exist in `src/shared/db/migrations.ts`. Only `lessons` and `app_settings` tables are currently defined.

2. **Incomplete PRD specification**: While the PRD (`attachments/07-phase1-prd-draft.md` §10) mentions the four tables conceptually, it lacks complete schema definitions:
   - ❌ `review_events` table: No column definitions for storing the `'remembered' | 'forgot'` rating
   - ❌ `review_sessions` / `review_session_items`: Purpose stated (crash recovery) but no structure defined
   - ⚠️ `flashcards`: Partial spec (constraints mentioned, but missing columns like `id`, `created_at`, `updated_at`)
   - ✓ `review_schedule`: Most complete, but missing some details

3. **DR-02 verification result**: The 2-outcome rating values (`'remembered'` and `'forgot'`) are confirmed in PRD §8 BR-REVIEW-002, but there's no defined column to store them yet.

### Recommended next steps:

1. **Schema design required**: Before promoting Stage 2 from backlog, complete the schema definitions for all four tables with explicit column names, types, and constraints
2. **Migration strategy**: PRD flags migration as "RISK cao nhất" — requires versioned, transaction-safe, idempotent approach (different from current "rerun array" pattern)
3. **Specifically for DR-02**: Define the exact column in `review_events` for storing ratings (recommended: `TEXT CHECK(rating IN ('remembered', 'forgot'))` with NULL for skips)
